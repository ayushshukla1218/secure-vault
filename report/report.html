Abstract

Organisations and individuals routinely maintain collections of passwords — for cloud services, databases, internal tools, and third-party platforms — that are either stored in plaintext (spreadsheets, sticky notes, shared documents) or entrusted entirely to proprietary vaults with no independently verifiable cryptographic guarantee of confidentiality or tamper-evidence. This project addresses that gap by designing and implementing SecureVault, a web-based password management application in which every stored password is encrypted with AES-256-CBC keyed on the user's master credential, the master credential itself is protected through a SHA-256 hash (never stored in plaintext), password exports are digitally signed using RSA-2048 (so a recipient can independently verify the export's authenticity and integrity), account recovery is facilitated through RSA public-key encryption of a recovery token, and every login, view, add, update, delete, and export action is permanently recorded in an immutable blockchain-style audit log.

Because the live application operates as a cryptographic demonstrator rather than a production backend with a historical database, a synthetic vault-access activity log (600 records across 150 simulated vault sessions, with approximately 7.2% of records deliberately marked as suspicious) was generated to support a supplementary machine-learning study. Features include access time, session duration, number of passwords accessed, master-password hash verification result, blockchain chain-integrity flag, and RSA export-signature validity. Four supervised algorithms — Logistic Regression, K-Nearest Neighbours, Decision Tree, and Random Forest — were implemented and evaluated using accuracy, precision, recall, F1-score, and confusion-matrix analysis under two feature scenarios: Scenario A (with cryptographic integrity flags) and Scenario B (metadata only).

Results confirm that all four algorithms classify perfectly when the cryptographic integrity columns are available, but detection collapses to near-random when restricted to access metadata alone — the same pattern observed in analogous encrypted-messaging studies. The project concludes that real, standards-based cryptography provides the tamper-evidence this system requires; machine learning serves only as a possible downstream anomaly-triage layer.

Chapter 1: Introduction

1.1 Introduction

Modern enterprises, development teams, and individual users routinely manage dozens to hundreds of credentials — database passwords, API keys, cloud-console logins, third-party service accounts, and internal tool credentials — that must be securely stored, selectively shared, audited, and occasionally exported to authorised parties. Traditional approaches to this problem range from entirely insecure (plaintext spreadsheets, sticky notes, shared group emails) to partially secure but unverifiable (proprietary password managers that offer no independently auditable cryptographic guarantee). This project, SecureVault, was undertaken to design and build a working password management system that addresses this gap using real, standards-based cryptography applied at multiple levels — AES-256 for stored passwords, SHA-256 for master credential protection, RSA-2048 for digital signing and recovery, and a blockchain-inspired hash chain for immutable audit history.

1.2 Motivation

The motivation for this project arises from three well-documented, recurring problems in credential management. First, credential leaks through plaintext or weakly encrypted storage remain among the most common and damaging data breach vectors: when a storage medium is compromised, all credentials stored without strong encryption are immediately exposed. Second, there is typically no cryptographic proof of who authorised a password export — a file of exported credentials can be forged, altered, or replayed with no mechanism for a recipient to detect that tampering. Third, audit trails in most password management systems are stored in the same mutable database as the passwords themselves, meaning an attacker with database write access can silently erase all evidence of access. Blockchain-style, hash-linked audit logs directly address the third problem, since any retroactive alteration to the chain breaks every subsequent hash and is therefore mathematically detectable.

1.3 Problem Definition

Existing credential storage solutions typically exhibit three related weaknesses: (i) passwords are encrypted at rest, but the encryption key is managed by the vendor and not independently verifiable by the user; (ii) exports of password collections carry no digital signature, so there is no cryptographic proof of origin or integrity; and (iii) access logs are stored in mutable datastores and can be modified without detection. The problem this project addresses is: how can a password management platform be built such that every stored password is encrypted with AES-256 keyed on the user's own master credential, the master credential is protected by a one-way SHA-256 hash, exports are digitally signed with RSA-2048, account recovery is facilitated through RSA encryption of a recovery token without ever transmitting the plaintext master credential, and every access event is recorded in an immutable, hash-linked blockchain audit log?

1.4 Objectives of Project

  • To design and implement a web-based password vault in which every stored password is encrypted using AES-256-CBC, with the encryption key derived from the user's master credential.
  • To protect the master credential using SHA-256 hashing, so that the plaintext master password is never stored or transmitted in any form.
  • To digitally sign password exports using RSA-2048, so that any recipient can independently verify both the origin and integrity of the exported data.
  • To implement RSA-based account recovery, enabling identity verification without transmitting the plaintext master password.
  • To record every vault action (login, add, view, update, delete, export) in an immutable, SHA-256 hash-linked blockchain audit log that detects any retroactive tampering.
  • To evaluate whether machine learning can serve as a complementary, automated layer for detecting suspicious vault access patterns on top of the cryptographic system.

1.5 Scope of the Project

The scope of this project covers the design and implementation of a client-server web application supporting user registration (with RSA key-pair generation), login (SHA-256 master credential verification), vault CRUD operations (AES-256-CBC encryption and decryption), digitally signed JSON exports (RSA-2048), RSA recovery token generation, and a blockchain audit log with chain-integrity verification. It also covers a supplementary data-science evaluation using a synthesised vault-access activity dataset. The scope explicitly excludes deployment on a multi-tenant cloud infrastructure with persistent database storage, integration with a production PKI or hardware security module, and browser-extension or mobile-app distribution — these are identified as future work rather than deliverables of this capstone project.

1.6 Application of the Project

  • Enterprise credential management: IT and DevOps teams store shared service credentials (cloud consoles, CI/CD pipelines, database passwords) with cryptographic guarantee of confidentiality and a tamper-proof audit trail for compliance.
  • Regulated industries (finance, healthcare): Organisations subject to SOC 2, ISO 27001, HIPAA, or similar frameworks require demonstrable access audit trails; the blockchain log provides immutable, independently verifiable evidence.
  • Secure credential transfer: The RSA-signed export allows an authorised employee or regulator to receive a password export and independently verify — using the organisation's published public key — that the file has not been altered since it was signed.
  • Academic and training contexts: The application serves as a working demonstrator of applied cryptography (AES, SHA-256, RSA) and blockchain-inspired data structures for students of Cryptography and Network Security.

1.7 Expected Outcome of the Project

The expected outcome is a fully functional, browser-based password vault demonstrating genuine multi-level encryption (not placeholder or simulated logic), along with a working export-signing demonstration, an RSA recovery mechanism, and an honestly evaluated machine-learning comparison identifying the boundary of what automated methods can and cannot contribute to anomaly detection in vault access patterns.

Chapter 2: Requirement Gathering, Analysis and Planning

2.1 Data Collection and Description

Because the SecureVault application is a live cryptographic demonstrator rather than a production system with an accumulated historical database, it does not by itself produce a ready-made dataset for machine-learning analysis. To support the ML component of this project (Chapters 3 and 4), a synthetic vault-access activity log was generated in Python to model the kind of session records the application would accumulate in real, sustained organisational use across many users and vault sessions.

Dataset size: 600 rows × 13 raw columns, generated across 150 simulated user accounts, each with 2–6 vault sessions. Approximately 7.2% of sessions (43 of 600) were deliberately marked as suspicious — representing unauthorised access attempts, brute-force login events, or tampered blockchain records — to create a realistic class-imbalanced anomaly-detection problem.

2.2 Data Processing / Preprocessing

The raw dataset was first checked for missing values — none were found, since every field is populated programmatically at generation time. Timestamps were decomposed into month, day-of-week, and hour-of-day components so temporal patterns (for example, after-hours access) could be modelled numerically. The two categorical columns (Event_Type, User_ID) were label-encoded into integers. A derived Integrity_Score feature was computed as the mean of the three binary integrity-check columns (Master_Hash_Valid, Chain_Intact, Signature_Valid), giving the models one compact summary feature alongside the individual flags. Session_Duration_s and Passwords_Accessed were standardised using z-score normalisation before use in distance-sensitive algorithms (KNN, Logistic Regression).

2.4 Algorithm Selection

Since the dataset carries a binary label (Suspicious_Flag), the vault anomaly detection task was framed as supervised binary classification. Four algorithms, spanning different modelling assumptions, were selected for comparison:

  • Logistic Regression — a linear, highly interpretable baseline.
  • K-Nearest Neighbours (k=5) — a non-parametric method requiring no assumption about the decision boundary's shape.
  • Decision Tree — produces human-readable if/else rules, valuable for an auditable security system.
  • Random Forest — an ensemble of decision trees, typically more robust to overfitting than a single tree.

2.5 Methodology

The dataset was split 75%/25% into training and test sets using stratified sampling to preserve the genuine-to-suspicious ratio in both splits. Two feature scenarios were evaluated for a fair comparison: Scenario A includes the cryptographic integrity-check columns (Master_Hash_Valid, Chain_Intact, Signature_Valid, Integrity_Score) as features; Scenario B withholds them, using only ordinary session metadata (Event_Type, timestamp decomposition, Session_Duration_s, Passwords_Accessed). All four algorithms were trained and evaluated under both scenarios using accuracy, precision, recall, F1-score, and confusion-matrix analysis, detailed in Chapter 3.

Chapter 3: System Design and Evaluation

3.1 Algorithm Implementation

The vault platform's cryptographic architecture follows a multi-level layered design applied per user account. When a user registers, a fresh RSA-2048 key pair is generated server-side. The master password is hashed with SHA-256 (never stored in plaintext) and used as the AES-256-CBC key-derivation input for all subsequent password encryption. The RSA private key is itself AES-encrypted with the master password before storage, so the private key is only recoverable when the correct master password is presented. Every vault action creates a new block in the SHA-256 hash-linked audit chain.

Core cryptographic implementation excerpt (server-side, crypto.js):

// AES-256-CBC — encrypt a password with master credential as key
function encryptAES(plaintext, masterKey) {
  const iv    = forge.random.getBytesSync(16);
  const key   = forge.md.sha256.create().update(masterKey).digest().bytes();
  const cipher = forge.cipher.createCipher('AES-CBC', key);
  cipher.start({ iv });
  cipher.update(forge.util.createBuffer(plaintext, 'utf8'));
  cipher.finish();
  return forge.util.encode64(iv) + ':' + forge.util.encode64(cipher.output.bytes());
}

// SHA-256 — hash master credential (never stored in plain)
function hashMaster(password) {
  return crypto.createHash('sha256').update(password).digest('hex');
}

// RSA-2048 — digitally sign an export payload
function signData(data, privateKeyPem) {
  const privateKey = forge.pki.privateKeyFromPem(privateKeyPem);
  const md = forge.md.sha256.create();
  md.update(JSON.stringify(data), 'utf8');
  return forge.util.encode64(privateKey.sign(md));
}

// Blockchain block — SHA-256 hash-linked audit record
class Block {
  constructor(index, data, previousHash) {
    this.index        = index;
    this.timestamp    = new Date().toISOString();
    this.data         = data;
    this.previousHash = previousHash;
    this.hash         = this.calculateHash();
  }
  calculateHash() {
    const content = this.index + this.timestamp +
                    JSON.stringify(this.data) + this.previousHash;
    return crypto.createHash('sha256').update(content).digest('hex');
  }
}

3.2 Model Evaluation

Verification of the cryptographic system works as follows: for AES decryption, the correct master password is required to reconstruct the key — an incorrect password produces garbled or failed output. For the RSA export signature, verifySignature(data, signatureB64, publicKeyPem) is called; any modification of the exported data — even a single byte — produces a verification failure. For the blockchain audit log, each block's hash is recomputed from its fields and compared to its stored hash; any retroactive alteration breaks the chain at exactly that block.

Table 6 — Confusion matrix outcome definitions

Scenario A's perfect scores across all four algorithms are expected rather than impressive: Master_Hash_Valid, Chain_Intact, and Signature_Valid are the very columns used to define the Suspicious_Flag label at generation time, so any reasonable classifier finds the near-deterministic rule connecting them. This scenario primarily confirms that the modelling pipeline (train/test split, standardisation, fitting, evaluation) is implemented correctly.

Scenario B is the fairer and more important test. With accuracy alone (0.927 for three of the four algorithms), the result would appear acceptable — but the confusion matrix reveals why that figure is misleading: True Positives = 0 and False Negatives = 11 for Random Forest, Logistic Regression, and KNN, meaning these models never once correctly identify a suspicious session. They simply predict 'Genuine' for every record, which is correct 92.7% of the time only because genuine sessions dominate the dataset (139 of 150 test records). Only the Decision Tree shows marginal sensitivity (recall = 0.091), and even this is more likely a symptom of overfitting to a small number of training examples than a generalisable pattern.

4.4 Discussion of Results & Limitations of the System

The cryptographic core of SecureVault performed exactly as designed: AES-256-CBC encryption is confirmed by observing decryption failure when the master password is incorrect; SHA-256 master hashing is confirmed by verifying that two different passwords produce different, irreversible hashes; RSA digital signature verification is confirmed by observing that any byte-level modification of the exported JSON causes the signature check to return false; and the blockchain audit log is confirmed to detect retroactive alteration by recalculating each block's hash on demand.

The system has three identifiable limitations. First, it uses an in-memory store rather than a persistent database, meaning vault data does not survive a server restart — this is explicitly by design for the capstone demonstrator and is identified as the primary production-readiness gap. Second, the RSA key pair is generated server-side and the private key is stored (AES-encrypted) in the same server memory as the vault data; a production deployment would generate keys client-side (in the browser) to ensure the server never has custody of the unencrypted private key. Third, as with the SecureChat study, ordinary session metadata (event type, timing, session duration, number of passwords accessed) carries essentially no signal about cryptographic anomalies in this system; any future work toward metadata-only anomaly detection would require either a fundamentally different feature set or a larger, more representative dataset of genuine adversarial access events.

Chapter 5: Conclusion

5.1 Summary of Work Completed

This project designed, implemented, and evaluated SecureVault, a multi-level encryption password management platform in which every stored password is encrypted with AES-256-CBC keyed on the user's master credential, the master credential is protected by SHA-256 hashing and never stored in plaintext, password exports are digitally signed with RSA-2048 so that recipients can independently verify authenticity and integrity, account recovery is facilitated through RSA public-key encryption of a recovery token, and every vault action is permanently recorded in a SHA-256 hash-linked blockchain audit log that detects any retroactive tampering — all performed using real, standards-based cryptographic primitives (node-forge library) rather than simulated logic.

The application supports user registration with automatic RSA key-pair generation, login with SHA-256 master-credential verification, full vault CRUD with AES-256-CBC encryption and on-demand decryption, digitally signed JSON export with downloadable proof, RSA recovery token generation, and a live blockchain audit log with chain-integrity checking.

A supplementary data-science study generated a synthetic vault-access activity dataset (600 records, 150 simulated sessions), performed exploratory data analysis, and implemented and compared four supervised classification algorithms (Logistic Regression, K-Nearest Neighbours, Decision Tree, and Random Forest) for automated suspicious-session detection. The evaluation, carried out honestly under two contrasted feature scenarios, established that these algorithms succeed only when given the cryptographic verification outputs directly, and are not capable of detecting suspicious sessions from ordinary vault-access metadata alone — a finding reported transparently rather than obscured, since it correctly identifies the boundary of what machine learning contributes to this system.

Overall, the project meets its stated objective: a password vault where credentials are encrypted, master access is hashed and never exposed, exports are digitally signed and independently verifiable, recovery is RSA-based, and every action creates a new linked, immutable blockchain record — with an honestly evaluated machine-learning layer identifying the limits of automated anomaly detection on top of real cryptography.

Complete source files (server.js, crypto.js, blockchain.js, store.js, routes.js, public/index.html, public/style.css, public/app.js — approximately 750 lines total) accompany this report as a separate project deliverable. The most important cryptographic core functions are reproduced below.

// ---- crypto.js: Core cryptographic primitives ----
const forge = require('node-forge');
const crypto = require('crypto');

// SHA-256 master credential hash — plaintext never stored
function hashMaster(password) {
  return crypto.createHash('sha256').update(password).digest('hex');
}

// AES-256-CBC encrypt — IV randomly generated per operation
function encryptAES(plaintext, masterKey) {
  const iv  = forge.random.getBytesSync(16);
  const key = forge.md.sha256.create().update(masterKey).digest().bytes();
  const cipher = forge.cipher.createCipher('AES-CBC', key);
  cipher.start({ iv });
  cipher.update(forge.util.createBuffer(plaintext, 'utf8'));
  cipher.finish();
  return forge.util.encode64(iv) + ':' +
         forge.util.encode64(cipher.output.bytes());
}

// AES-256-CBC decrypt
function decryptAES(ciphertext, masterKey) {
  const [ivB64, enc] = ciphertext.split(':');
  const iv  = forge.util.decode64(ivB64);
  const key = forge.md.sha256.create().update(masterKey).digest().bytes();
  const decipher = forge.cipher.createDecipher('AES-CBC', key);
  decipher.start({ iv: forge.util.createBuffer(iv) });
  decipher.update(forge.util.createBuffer(forge.util.decode64(enc)));
  decipher.finish();
  return decipher.output.toString('utf8');
}

// RSA-2048 key pair — generated at registration
function generateRSAKeyPair() {
  const kp = forge.pki.rsa.generateKeyPair({ bits: 2048 });
  return {
    publicKey:  forge.pki.publicKeyToPem(kp.publicKey),
    privateKey: forge.pki.privateKeyToPem(kp.privateKey)
  };
}

// RSA OAEP encrypt — for recovery token
function encryptWithRSA(plaintext, publicKeyPem) {
  const pub = forge.pki.publicKeyFromPem(publicKeyPem);
  return forge.util.encode64(pub.encrypt(plaintext, 'RSA-OAEP'));
}

// Digital signature — RSA sign over SHA-256 digest of export payload
function signData(data, privateKeyPem) {
  const priv = forge.pki.privateKeyFromPem(privateKeyPem);
  const md   = forge.md.sha256.create();
  md.update(JSON.stringify(data), 'utf8');
  return forge.util.encode64(priv.sign(md));
}

// Verify digital signature
function verifySignature(data, signatureB64, publicKeyPem) {
  try {
    const pub = forge.pki.publicKeyFromPem(publicKeyPem);
    const md  = forge.md.sha256.create();
    md.update(JSON.stringify(data), 'utf8');
    return pub.verify(md.digest().bytes(), forge.util.decode64(signatureB64));
  } catch { return false; }
}

// ---- blockchain.js: Immutable hash-linked audit log ----
class Block {
  constructor(index, data, previousHash) {
    this.index        = index;
    this.timestamp    = new Date().toISOString();
    this.data         = data;
    this.previousHash = previousHash;
    this.hash         = this.calculateHash();
  }
  calculateHash() {
    const c = `${this.index}${this.timestamp}` +
              `${JSON.stringify(this.data)}${this.previousHash}`;
    return crypto.createHash('sha256').update(c).digest('hex');
  }
}

class AuditBlockchain {
  constructor() { this.chain = [this.createGenesis()]; }
  createGenesis() {
    return new Block(0, { event:'GENESIS', message:'Vault initialized' }, '0');
  }
  addBlock(data) {
    const block = new Block(
      this.chain.length, data, this.getLatestBlock().hash);
    this.chain.push(block);
    return block;
  }
  isChainValid() {
    for (let i = 1; i < this.chain.length; i++) {
      if (this.chain[i].hash !== this.chain[i].calculateHash()) return false;
      if (this.chain[i].previousHash !== this.chain[i-1].hash) return false;
    }
    return true;
  }
}
